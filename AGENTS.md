# Working preferences

- The user runs downloads and analysis themselves. Edit source code, tests, and project instructions. Perform filesystem cleanup when explicitly requested. Do not execute downloaders, data conversions, database builds, analysis, or tests unless the user explicitly asks you to run them.
- Sportmonks is the primary football data provider. TFF Fantasy statistics may be kept as a separate supplemental CSV source. Do not add API-Football code or credentials.
- Use Sportmonks player IDs as cross-provider player keys. Never auto-assign ambiguous name matches; write a review report and require an explicit override.
- Keep CSV as the analysis/exchange format, including caches and reports. SQLite is allowed for the final structured dataset and SQL queries. Do not create duplicate JSON exports or JSON-encoded CSV cells.
- Python stages share one definition of match states, blank numbers, CSV reading and writing, season names and UTC timestamps in `src/shared.py`. Use it rather than writing another copy, and keep its state lists in step with `src/web/core/match-rules.js`.
- JSON parsing is allowed only in memory to decode provider HTTP responses.
- Do not delete or convert previously downloaded files without an explicit request.
- Keep API credentials local and never print their values. The one exception is the Supabase publishable (anon) key in `src/web/core/auth-config.js`, which is public by design; the Supabase secret/`service_role` key is a credential and never goes in the site or the repository.
- Visitor accounts and profiles live in Supabase (Postgres), not in the CSV pipeline. Their schema is `supabase/*.sql`, run by the user in the Supabase SQL Editor; every table gets row-level security that limits each visitor to their own rows, and a change to a table is a change to its SQL file.
- Keep lossless provider captures under `data/raw`, rebuildable caches and reports under `data/temp`, and website-ready CSVs under `data/final`.
- Keep the unified SQLite database at `data/superlig.sqlite`. Preserve reviewed identity overrides under `config/`; they are not temporary data.
- The public site (fantezianaliz.com, Cloudflare Pages) is the files-only build that `src/web/build_static.py` writes to `data/temp/site`, with website code from GitHub `main` as pushed and data from `data/final`; nothing reaches the public site until it is pushed. Anything that needs `src/web/serve.py` at request time, such as live scores or Kadro Kur recommendations, must stay off unless `siteMode` (in `src/web/core/site.js`) is `"local"`. Never publish `.env`, `data/raw`, or `assets/face-portraits/`. `src/update_site.py` runs in GitHub Actions (`.github/workflows/update-site.yml`) and publishes on its own, including the TFF export (about once a day, when the TFF login secrets exist) and the odds forecast; both are optional steps that must never stop the site update. `.github/workflows/research.yml` runs the research reports weekly. Each update step is a command that can also be run by hand, so when one changes, change `update_site.py` and the workflow together. Between runs the data lives in Cloudflare R2 (bucket `fantezianaliz-data`), which is the main copy of `data/final`; `src/sync_data.py` copies it to and from this computer and never deletes anything. Credentials for the cloud run are GitHub secrets, never files in the repository.
- The project exists to pick a better TFF fantasy XI. The odds model is a means to that end: judge new modelling work by whether it improves a fantasy input (clean-sheet probability, fixture difficulty, expected minutes), not by whether the match model gets marginally sharper.
- Every page of the website agrees with every other: one look (Kadro Kur's pitch, `src/web/styles/pitch.css`), one rule per number (`src/web/core/match-rules.js`, `src/web/core/locale.js`) and one Turkish word per concept. New pages reuse these rather than writing their own.
- Charts, bars and legends that compare clubs draw each club in its official colour from `teamColor()` / `teamColorPair()` in `src/web/core/team-colors.js`; text stays in the ink colours. Use the colours as published by the club, not hand-picked shades.
- Check every website change in dark mode as well as light; the user browses in dark. Use the theme variables (`var(--surface)`, `var(--surface-raised)`, `var(--surface-soft)`, `var(--field)`, `var(--ink)`, `var(--muted)`, `var(--line)`) rather than literal colours such as `white`; only accent colours need their own dark variant.
- Fantasy scoring rules live in `config/tff_scoring_rules.csv`. They are transcribed from a supplied rules graphic, not from a provider feed, so treat them as reviewed reference data: change them only when the user supplies a new source, and keep the `needs_confirmation` flag honest.
